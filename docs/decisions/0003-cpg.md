# 0003 — Deterministic Code Property Graph (CPG) overlay

- **Status:** Accepted (amended 2026-07-07: K3a completeness — `?`-operator,
  labeled jumps, expression-position policy, closure/macro policy, C# overlay)
- **Date:** 2026-07-06

## Context
The base graph answers *who declares / calls / uses whom* at symbol grain. The
next questions — "what executes after this?", "where does this value come
from?" — need **intra-function control flow and data flow**. The ontology
already carries both edge kinds: `FLOWS_TO` and `DATA_DEP` are live today for
Salesforce Flows, where the *elements* of a declarative workflow are the flow
steps. Real code has no such element nodes: a `Function` is one node, and its
body is (by ADR-0001) a lossless balanced **token tree**, not a statement AST.

Two architectural constraints bind the design:

1. **Extractors cannot see source.** An `Extractor` is graph→graph
   (`src/extract/mod.rs`); the CST is gone by the time it runs. A CPG needs the
   token tree, so **the CPG is not an extractor** — it is a lowering concern.
2. **Golden output must not move.** The base `graph` command output is pinned
   by the corpus regression gate; the CPG must be strictly additive and
   opt-in.

## Decision
**The CPG is an opt-in second lowering pass, exposed as `trailtracker cpg
[DIR]`.** It emits the ordinary base graph **plus** an overlay, per Rust
function with a body:

- **`Statement` nodes** (new ontology node kind) — one per statement, produced
  by deterministic segmentation of the function's `Block` token tree, plus one
  **virtual exit node** per function (`virtual: true`, `role: "exit"`).
- **`FLOWS_TO` edges** — statement→statement control flow: sequence, if/else
  branch + merge, loop body + back-edge + exit, match arms + merge, early
  `return`/`break`/`continue`, and a `Function → first-statement` entry edge.
- **`DATA_DEP` edges** — intra-function def-use chains, **consumer →
  producer** (the dependency direction, exactly as the ontology documents for
  Salesforce): the reading statement points at every definition site that may
  reach it.

### Placement: a front-end hook, not a pipeline special case
`LanguageFrontEnd` gains one defaulted method:

```rust
fn lower_cpg(&self, input: &LoweredInput, graph: &mut Graph) {
    self.lower(input, graph); // default: no overlay
}
```

Only the Rust front end overrides it (calling `ir::lower` with the CPG flag);
the other 55 front ends are untouched and simply produce their base facts. The
pipeline grows `analyze_dir_opts(root, AnalyzeOptions { cpg })`;
`analyze_dir` delegates with `cpg: false`, so every existing caller is
byte-identical. The overlay emission runs inside the same lowering pass that
builds `PendingFn`, so **statement nodes attach to the exact same function ids
the base graph uses** — no id-derivation drift by construction.

### Node kind: new `Statement`, not reuse
Reusing `Function` grain is impossible (one node per function). Reusing the
Salesforce flow-element modelling would smuggle workflow vocabulary into code.
A first-class `node::STATEMENT` keeps the lattice honest: statements are
contained by their function (`Function -CONTAINS-> Statement`, consistent with
the CONTAINMENT super-relation), and `FLOWS_TO`/`DATA_DEP` keep one meaning
everywhere: *execution proceeds* / *value is consumed*.

### Identity and determinism
- Function id (existing): `fn::{qual}#{line}`.
- Statement id: `stmt::{qual}#{line}::{n}` where `n` is the statement's index
  in a fixed pre-order segmentation walk. Exit: `stmt::{qual}#{line}::exit`.
- Props: `line`, `span_start`, `span_end`, `stmt_kind`
  (`let|expr|if|while|for|loop|match|return|break|continue|item|arm`); node
  `name` is the whitespace-collapsed statement text truncated to 48 chars.
- Everything is emitted through the de-duplicating `BTreeMap` graph API; same
  input ⇒ byte-identical JSONL. No HashMap, no randomness, std-only,
  `forbid(unsafe_code)`.

### Segmentation over the token tree (grammar facts, not heuristics)
Bodies are balanced token trees; groups are atomic, so a `;` inside a nested
group is invisible at statement level. Statements are cut at depth-0 `;`, or
at the body group of a block construct. Rust **bans bare `{`-expressions in
`if`/`while`/`for`/`match` headers**, so the first depth-0 `Brace` after the
keyword is *always* the body/arm list — a grammar guarantee, not a guess.
Item declarations in statement position (`fn`, `struct`, …) are segmented as
`item` statements; control flows through them trivially (they do not execute).
Bare `{ … }` / `unsafe { … }` block statements are spliced inline (their inner
statements join the enclosing sequence; no wrapper node).

### FLOWS_TO edge vocabulary
Edge props carry `role` — one of `entry`, `seq`, `branch` (+ `branch:
then|else|arm|body`), `loop-back` (+ `back_edge: true`), `loop-exit`,
`return`, `break`, `continue` — so every edge is auditable. Divergent
statements (`return`, `break`, `continue`, a `loop` with no `break`)
contribute **no** fall-through edge: absence of flow is information.

### DATA_DEP: conservative may-reach, ambiguity preserved
Per the resolution-ladder philosophy, the CPG never picks a winner it cannot
prove:

- Definition sites: `let` patterns, `x = …` / `x op= …` assignments to a bare
  name, `for` pattern bindings, match-arm pattern bindings, and function
  parameters (def site = the `Function` node, `def: "param"`).
- A **use** links to **every** definition that may reach it: an unconditional
  redefinition *replaces* the live-def set; a definition inside a branch/arm/
  loop *joins* it (both the old and new defs stay live at the merge).
  Loop bodies are scanned twice so uses before a def see the previous
  iteration's def through the back-edge (the second pass only adds edges; the
  graph API dedups).
- **No aliasing claims:** `x.f = v` and `*p = v` are treated as *reads* of
  `x`/`p`, never as kills or new defs. `&mut` reborrows are just reads.
- `let`-bound names are block-scoped (defs die at block exit); assignments to
  outer names survive the block (joined into the outer set).

### `?`-operator: an explicit try-exit edge (amendment, K3a)
`expr?` is an implicit early exit. Any statement (or flat match-arm body)
whose **depth-0** token run contains a try `?` gains one additional
`FLOWS_TO → exit` edge with `role: "try-exit"`; its ordinary exits remain the
Ok path. Two deliberate boundaries, both grammar-grounded:

- **`?Sized` is not control flow.** Angle brackets are not token-tree groups,
  so a relaxed bound in a `let` ascription (`let x: Box<dyn W + ?Sized>`) sits
  at depth 0. Disambiguation: a try `?` is never directly followed by a
  non-keyword identifier, while `?Sized`/`?Trait` always is. That token pair is
  the discriminator — a fact of the surface grammar, not a heuristic.
- **Nested groups are not scanned.** A `?` inside a group may belong to a
  closure body (`g(|| h()?)`), which exits the *closure*, not the function.
  Token trees cannot distinguish an argument-position try (`g(h()?)`, a real
  early exit) from a closure-body try without parsing expressions, so neither
  is claimed: a documented under-approximation — absence over fabrication.

### Labeled `break`/`continue` (amendment, K3a)
Loop statements record their `'label`; `break 'l`/`continue 'l` (statement or
flat arm-body form) target the innermost **matching** loop context, not the
innermost loop. A label with no matching loop — in practice a labeled bare
block, which segmentation splices inline — produces **no** edge: the target is
a block exit the CPG does not model, and a wrong edge is worse than a missing
one. Unlabeled jumps keep targeting the innermost loop, exactly as before.

### Expression-position control flow: statement grain, defended (K3a)
`let x = if c { a() } else { b() };` is **one** `Let` statement — the CPG does
not decompose control flow in expression position (`if`/`match`/`loop` as an
expression inside a larger statement). This is a decision, not an oversight:

1. **Partial decomposition is a false promise.** Expression-position branching
   arrives in many shapes — `if`/`match` expressions, short-circuit `&&`/`||`,
   `.then()`/`.map_or()` chains, try blocks. Decomposing only the syntactically
   obvious `if`/`match` cases would make the overlay's precision depend on
   surface style: two equivalent programs (one using an if-expression, one
   using `&&`) would get different granularity, which is poison for an
   equivalence checker that must treat grain as a contract.
2. **The statement-id scheme is a stable contract.** Ids are a pre-order index
   over the statement segmentation; sub-statement nodes would either break the
   scheme or bolt a second id grammar onto one construct.
3. **DATA_DEP already behaves like a merge.** All tokens of both branches
   attribute to the enclosing statement, so a use links to every def reaching
   either branch — exactly the union a decomposed merge would produce for the
   may-reach question.

**What the equivalence checker therefore cannot distinguish:** two rewrites
that differ *inside* an expression-position construct (swapped branch bodies,
inverted condition with swapped arms) present identical CFG shape at statement
grain; equivalence for such statements must fall back to token/tree-level
comparison of the statement text. Also, an assignment to an outer variable
inside an expression-position block (`let y = if c { x = 1; 2 } else { 3 };`)
is seen as a *read* of `x`, not a def — same no-kill conservatism as closures,
documented here so no one mistakes it for precision.

### Closures and macros: opaque by policy (K3a)
- **Closures are opaque calls.** A closure body is not a separate CFG and is
  not walked for control flow: its tokens' reads attribute to the enclosing
  statement (may-reach, no kills), its internal `return`/`?` exit the closure
  and are not claimed, and defs inside it never kill outer defs. Rationale:
  closure execution is deferred and possibly repeated or never — any FLOWS_TO
  claim about *when* the body runs would be fabricated. Consequence for
  equivalence checking: rewrites inside a closure body are invisible at CFG
  grain (token-level comparison required); a rewrite that moves code across a
  closure boundary *is* visible (the def-use attribution moves between
  statements).
- **Macros are untouched.** A macro invocation is a single `expr` statement;
  post-expansion tokens are unavailable by construction (no compiler, no
  expansion), so no flow inside or out of a macro is claimed beyond the
  statement's position in the sequence. Its argument tokens are scanned for
  reads (attributed to the statement, same as closures); a macro that expands
  to control flow (`return`, loops) is a documented blind spot. Consequence:
  equivalence across macro boundaries reduces to byte/token equality of the
  invocation.

### C# — language #2 via `lower_cpg` (amendment, K3a)
The C# front end overrides `lower_cpg` (the seam built for exactly this);
`src/lang/csharp/cpg.rs` mirrors the Rust overlay — same `Statement` nodes,
same id scheme (`stmt::{qual}#{line}::{n}` + `::exit`), same edge vocabulary,
same may-reach `DATA_DEP` machinery (branch envs union at merges, loop bodies
walked twice for back-edge visibility, `let`-analog declarations block-scoped,
no aliasing claims: `x.F = v` is a read of `x`). C#-specific decisions:

- **Statement grammar:** `if`/`else` (embedded single-statement bodies are
  parsed recursively — `if (c) A();` is real C#), `while`, `do…while`, `for`,
  `foreach`, `switch` sections (stacked `case`/`default` labels form one arm),
  `using`/`lock`/`fixed` (a node + sequential body, no branch claimed),
  `checked`/`unchecked`/`unsafe` blocks spliced like Rust bare blocks, local
  functions segmented as non-executing `item` statements.
- **`break` binds to the nearest loop OR switch** (C# semantics — the break
  stack is separate from the continue stack, which is loops-only).
- **`do…while` shares the loop edge shape** (`branch/body`, `loop-back`,
  `loop-exit` at the header node): the ≥1-iteration guarantee is not
  expressible in may-flow edges; the `stmt_kind: "do"` carries it. Similarly,
  every C# loop gets a `loop-exit` edge — C# has no `loop` keyword, so an
  infinite `for(;;)` is not a grammar fact and gets a (spurious but
  conservative) exit edge.
- **`throw` → function exit** (role `throw`), like an early return. A throw
  that a *local* catch would intercept still edges to the exit; the local-
  catch path is covered at section grain by the try edge below. Chosen over
  per-statement throw→catch edges, which the token tree cannot justify.
- **`try`/`catch`/`finally` policy — catch is a may-transfer branch of the
  `try` statement**: `try -branch/try-> body`, `try -branch/catch-> catch_i`;
  try-body and catch-body exits merge, and a `finally` block is a mandatory
  merge target all of them flow through. Rejected alternative: an edge from
  every try-body statement to every catch (O(n·m) fabrication — the CPG
  cannot know which statements can throw). Consequence for equivalence
  checking: the CFG says *which* catch clauses exist and what runs in them,
  not which statement transfers to them; `return`-inside-`try` does not route
  through `finally` in the graph (documented under-claim). Data flow matches:
  a catch body's env is the union of pre-try and post-try states (the catch
  may run after any prefix of the try block).
- **`goto` (label / `goto case`) diverges with no edge** — target unmodeled.
- **Def sites:** typed/`var`/multi-declarator locals (`local`), bare-name
  assignments (`assign`, compound ops read first), `for`-initializer
  declarations (def at the `for` node, self-reads in cond/incr), `foreach`
  iteration variables incl. tuple deconstruction (`loop`), `catch (T e)`
  bindings (`pattern`, scoped to the clause), parameters (`param` at the
  function node). Not claimed: `out var x` args, `is`-pattern variables,
  deconstruction assignments, chained-assignment inner defs — all documented
  under-claims; their *reads* still attribute to the statement.
- **Named arguments are not colon-skipped** in reads: `f(count: n)` vs a
  ternary's `c ? a : b` are indistinguishable at token grain, and a spurious
  read on a rare collision is the conservative direction for may-reach.
- **Top-level-statement entry markers get no overlay**: the synthetic `main`
  shares one fn id across several statement blocks, so statement numbering
  would collide; excluded, not special-cased.
- **Fixture:** `eval/corpus/dotnetlib` (golden-gated like every corpus case);
  `Scorer.Score` has a hand-verified CFG asserted edge-for-edge in
  `hand_verified_cfg_for_score` / `hand_verified_data_deps_for_score`.

### Honest limitations (recorded, not hidden)
- `?` inside a nested group (argument position or closure body) is not
  claimed as an exit — see the try-exit amendment above.
- A labeled bare block's `break 'label` has no modeled target (no edge).
- `let … else { … }` divergence is not modeled; the else block's tokens are
  scanned for reads only.
- Expression-position control flow is atomic — see the amendment above.
- Closure bodies and macro invocations are opaque — see the policy above.

## Alternatives considered
1. **CPG as an extractor.** Rejected: extractors cannot see the CST; rebuilding
   statement structure from the graph is impossible without fabricating.
2. **Always-on emission in `graph`.** Rejected: moves every golden; violates
   the additive contract; statement grain is not always wanted.
3. **Reuse `Function` nodes with span props for flow endpoints.** Rejected:
   collapses all intra-function flow onto one node — no chains, no branches.
4. **Full dataflow lattice / SSA.** Rejected for this slice: the conservative
   may-reach set is sound for the "where could this value come from" question,
   costs an order of magnitude less, and never claims more than it knows.

## Consequences
- `trailtracker cpg DIR` output is a strict superset of `trailtracker graph
  DIR` output (same lines, plus Statement/FLOWS_TO/DATA_DEP records).
- Goldens, `graph`, `stats`, extractors: byte-identical, untouched.
- The Salesforce and code worlds now share one flow vocabulary: a Flow
  connector and a Rust statement edge are the same `FLOWS_TO` at different
  grain, which is exactly what the cross-language Atlas is for.
- Other languages can adopt the overlay by overriding `lower_cpg` when their
  front ends are ready; nothing else changes.
